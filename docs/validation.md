Вход через http://127.0.0.1:8080 ранее возвращал 403 из-за APP_URL,
настроенного на localhost. В development разрешены локальные имена

выхода — 401. Запросы без CSRF-токена, с чужим Origin и другим портом
возвращают 403. В браузере на 127.0.0.1 выполнены вход и выход обеих
ролей, загрузка профиля кандидата и списка кандидатов работодателя.

## Варианты заданий

Команда `go run ./cmd/evaluate` проверяет версию 2026.10-v2.
Для каждой из девяти категорий создаются 100 новых вариантов,
seed=2..101. Готовый ключ от seed=1 переносится без решения новых условий.

| Категория | Различных условий из 100 | Прошли с чужим ключом | Прошли со своим правильным ключом |
| --- | ---: | ---: | ---: |
| backend / junior | 100 | 9 | 100 |
| backend / middle | 100 | 3 | 100 |
| backend / senior | 100 | 3 | 100 |
| frontend / junior | 100 | 1 | 100 |
| frontend / middle | 100 | 1 | 100 |
| frontend / senior | 100 | 9 | 100 |
| analytics / junior | 100 | 3 | 100 |
| analytics / middle | 100 | 0 | 100 |
| analytics / senior | 100 | 2 | 100 |
| Всего | 900 | 31 | 900 |

Перенос готового ключа позволяет пройти 31/900 тестов, около 3,4%.
Правильные ключи проходят 900/900. Отдельные unit-тесты проверяют
детерминированность генерации, единый состав тем, пустые ответы,
порог 4/6 и 5/6, отсутствие приватных ответов в публичном JSON.

Результат подтверждает вариативность условий и работу проверяющего кода.
Он не доказывает точность присвоения реального грейда, равенство сложности
между вариантами или устойчивость к решению с помощью LLM.
Банк шаблонов пока компактен, часть концептуальных вопросов повторяется.
Полный отчёт: [assessment-validation.json](assessment-validation.json).

## Подбор

В [matching-dataset.json](matching-dataset.json) заранее заданы восемь
профилей и двенадцать потребностей с ручной разметкой релевантных кандидатов.
Автономная команда `go run ./cmd/evaluate-matching` использует настоящий
парсер и функцию ранжирования. Она не обращается к HTTP API и БД.

Значение k равно 1 или 2 согласно разметке запроса. Недостающая позиция
считается нерелевантной. Precision@k равна числу релевантных кандидатов
среди первых k, делённому на k. Среднее по двенадцати запросам: **1,00**.

Проверены потребности для Go, Python и React, а также аналитики с SQL.
Есть сравнение внутри backend / middle: для Go первым идёт Александр,
для Python и Docker — Максим без истории ФСП. Запросы без грейда
проверяют ранжирование между несколькими уровнями.

Ограничение: набор совпадает с демоданными разработки. Во многих запросах
категория оставляет одного или двух человек. Поэтому 1,00 служит
регрессионным ориентиром, а не оценкой качества реального подбора.
Полный отчёт: [matching-validation.json](matching-validation.json).

Для повторения через работающий HTTP API предусмотрен
`scripts/benchmark-matching.ps1`. Выполнены все 12 запросов через работающий
HTTP API: средняя precision@k — 1,00. Отчёт сохранён в
[matching-http-validation.json](matching-http-validation.json).
Правила доступа и основные фильтры отдельно проверены интеграционным тестом.

## Следующая валидация

1. Независимые эксперты размечают грейды и релевантность пар до настройки
   алгоритмов. Данные настройки и проверки разделяются.
2. По тестированию измеряются согласие с экспертом, стабильность грейда,
   сложность и дискриминативность заданий. Проверяются перенос решений,
   угадывание и помощь LLM; пополняется банк.
3. По подбору измеряются precision@5, nDCG@5, полнота по категориям,
   доля принятых приглашений и время до первого контакта.
4. Сквозной сценарий проходят реальные кандидаты и работодатели.
   Фиксируются ошибки, понятность объяснений и время выполнения.
5. На стенде с PostgreSQL и Redis проводится нагрузочная проверка
   десятков одновременных пользователей. Такой прогон пока не выполнен.
