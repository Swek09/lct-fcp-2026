| Экспорт OpenAPI без БД | Работает, PDF имеет application/pdf |

Интеграционный тест проверяет роли и доступ к чужим данным, скрытие
контактов до принятия приглашения, изоляцию между работодателями,
CSRF и Origin, зарплатную вилку, статусы и дубли приглашений,
регистрацию и одноразовое подтверждение почты, тесты и интервалы,
серверный дедлайн, сохранение прежнего грейда при неудаче,
PDF, восстановление пароля и отзыв старых сессий, OpenAPI без ответов,
сохранение категории при удалении сессии из Redis.

Для вакансий и откликов проверены черновики, публикация, зарплатная вилка,
доступ владельца, согласие на контакт, отзыв отклика и повторная подача.
Одновременные отклики не создают дубль. Контакты, паспорт квалификации
и избранное скрытого профиля доступны только компании с действующим
согласием; отзыв отклика закрывает этот доступ. Статистика кабинета
ограничена данными владельца. Паспорт реальной попытки содержит темы,
версию, дату и результат, но не правильные ответы.

Для коротких задач проверены доступ по категории и роли, приватность решений,
отсутствие email кандидата, авторство задачи, запрет повторной проверки,
недельный интервал и одновременная отправка разных задач. При отрицательной
обратной связи дата практики не обновляется; поздняя положительная проверка
сохраняет дату выполнения, а не проверки. Задача другой категории не меняет
актуальность текущего профиля. Грейд и балл теста сохраняются.

Полный запуск go test ./... -count=2 с TEST_DATABASE_URL и TEST_REDIS_URL
прошёл дважды подряд с реальными БД; go vet ./... также пройден.
Счётчики ограничения запросов изолированы для каждого прогона, чтобы
повторные проверки не исчерпывали лимиты общих демоаккаунтов.
GitHub Actions выполняет эти проверки с настоящими PostgreSQL и Redis, затем
проверяет контейнеры перед деплоем и HTTPS после него. Подробности: [ci.md](ci.md).
Автоматических браузерных E2E в workflow пока нет.

Вход через http://127.0.0.1:8080 ранее возвращал 403 из-за APP_URL,
настроенного на localhost. В development разрешены локальные имена
localhost, 127.0.0.1 и [::1] при совпадении протокола и порта.
В остальных режимах проверка Origin остаётся точной.
Через работающий HTTP API проверены кандидат на 127.0.0.1 и работодатель
на localhost: вход и чтение сессии — 200, выход — 200, сессия после
выхода — 401. Запросы без CSRF-токена, с чужим Origin и другим портом
возвращают 403. В браузере на 127.0.0.1 выполнены вход и выход обеих
ролей, загрузка профиля кандидата и списка кандидатов работодателя.

## Варианты заданий

Команда `go run ./cmd/evaluate` проверяет версию 2026.10-v4.
Девять категорий, 18 доступных семейств в каждой: 162 семейства всего.
Каждый вариант содержит 12 заданий: по два разных семейства на каждую из шести тем.
Для каждой категории создаются 100 вариантов, seed=2..101.
Ключ от seed=1 переносится без решения новых условий.

| Категория | Различных условий из 100 | Прошли с чужим ключом | Прошли со своим правильным ключом |
| --- | ---: | ---: | ---: |
| backend / junior | 100 | 0 | 100 |
| backend / middle | 100 | 0 | 100 |
| backend / senior | 100 | 0 | 100 |
| frontend / junior | 100 | 0 | 100 |
| frontend / middle | 100 | 0 | 100 |
| frontend / senior | 100 | 0 | 100 |
| analytics / junior | 100 | 0 | 100 |
| analytics / middle | 100 | 0 | 100 |
| analytics / senior | 100 | 0 | 100 |
| Всего | 900 | 0 | 900 |

Правильные ключи проходят 900/900. Перенос ключа проходит 0/900.
Unit-тесты проверяют достижимость всех 162 семейств, две задачи на тему,
равное число числовых и концептуальных заданий, воспроизводимость,
разные условия без учёта перестановки ответов, порог 8/12 и 9/12,
агрегацию тем, сохранение оценки старых шестизадачных попыток,
запятую в числах, отклонение NaN/Infinity и отсутствие ключа в публичном JSON.
Сложные расчёты дополнительно решаются в тестах по тексту публичных условий.

Это механическая проверка генератора и оценки. Она не доказывает точность
реального грейда, равенство сложности вариантов или устойчивость к LLM.
Независимая экспертная калибровка пока не проведена. Концептуальные кейсы
могут повторяться между попытками; генератор не обещает абсолютную уникальность.
Отчёт: [assessment-validation.json](assessment-validation.json).
Состав банка: [assessment-bank.md](assessment-bank.md).

## Подбор

В [matching-dataset.json](matching-dataset.json) заданы двенадцать
профилей и пятнадцать потребностей с явной разметкой релевантных кандидатов.
Автономная команда `go run ./cmd/evaluate-matching` использует настоящий
парсер и функцию ранжирования. Она не обращается к HTTP API и БД.

Значение k равно 1, 2 или 3 согласно разметке запроса. Недостающая позиция
считается нерелевантной. Precision@k равна числу релевантных кандидатов
среди первых k, делённому на k. Среднее по пятнадцати запросам: **0,9667**.
Два базовых алгоритма при тех же фильтрах — только балл теста и балл
теста с бонусом ФСП — дают **0,8333**. Учёт запрошенного стека добавляет
13,33 процентного пункта на этом наборе.

Проверены потребности для Go, Python и React, а также аналитики с SQL.
Есть сравнение внутри backend / middle: для Go первым идёт Александр,
для Python и Docker — Максим без истории ФСП. Запросы без грейда
проверяют ранжирование между несколькими уровнями.

Ограничение: небольшой набор совпадает с демоданными разработки, разметка
ручная и не независимая. Во многих запросах категория оставляет одного
или двух человек. Метрики служат регрессионным ориентиром и сравнением
алгоритмов на одних данных, а не оценкой качества реального найма.
Полный отчёт: [matching-validation.json](matching-validation.json).

Для повторения через работающий HTTP API предусмотрен
`scripts/benchmark-matching.ps1`. Он читает тот же набор и проверяет
выдачу работающего HTTP API; результат сохранён в
[matching-http-validation.json](matching-http-validation.json).
Правила доступа и основные фильтры отдельно проверены интеграционным тестом.

## Следующая валидация

1. Независимые эксперты размечают грейды и релевантность пар до настройки
   алгоритмов. Данные настройки и проверки разделяются.
2. По тестированию измеряются согласие с экспертом, стабильность грейда,
   сложность и дискриминативность заданий. Проверяются перенос решений,
   угадывание и помощь LLM; пополняется банк.
3. По подбору измеряются precision@5, nDCG@5, полнота по категориям,
   доля принятых приглашений и время до первого контакта.
4. Сквозной сценарий проходят реальные кандидаты и работодатели.
   Фиксируются ошибки, понятность объяснений и время выполнения.
5. Провести длительную проверку с независимыми сессиями десятков
   пользователей, записью и большой базой. Короткий прогон чтения
   с параллельностью 20 этой проверки не заменяет.
