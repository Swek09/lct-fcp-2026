# Сценарий выступления

Презентация: docs/delivery/fsp-career.pptx, восемь слайдов.
Ориентир по длительности: 4-5 минут плюс демонстрация.

## 1. ФСП Карьера

Кандидат подтверждает квалификацию и получает предложения.
Работодатель начинает разговор сам. Сервис связывает две стороны
через подтверждённую категорию, а зарплата видна до принятия.

## 2. Механика обратного найма

Показать последовательность: профиль и тест, поиск работодателя,
приглашение с зарплатой, решение кандидата. Подчеркнуть, что
принятие раскрывает контакт только отправителю этого приглашения.

## 3. Подтверждение категории

В MVP три направления и три грейда. Кандидат выбирает предполагаемый
уровень. Вариант содержит шесть заданий за двадцать минут. Пять
правильных ответов подтверждают категорию. Смена подтверждённой
категории ограничена девяноста днями. Неудача не понижает грейд.

Пояснить, что условия меняются по параметризованным шаблонам, а оценку
вычисляет сервер. Это стартовая механика, требующая экспертной калибровки.

## 4. Объяснение подбора

Категория сначала задаёт фильтр. Затем результат теста даёт до 50
баллов, совпадение навыков до 40, достижения ФСП до 10. Навыки в
резюме остаются самоописанными; тест подтверждает общую категорию.
Каждая строка выдачи объясняет вклад факторов. История ФСП даёт бонус,
её отсутствие не закрывает доступ к подбору.

## 5. Рабочий прототип

Переключиться в браузер по docs/demo.md. Показать работодателя,
подборку, скрытый контакт и приглашение. Принять предложение
кандидатом и вернуться к работодателю.

Скриншот на слайде иллюстрирует интерфейс с синтетическими данными.
До выступления проверить, что Docker работает и нужный статус
приглашения соответствует плану показа.

## 6. Проверка вариантов

Проверены 900 новых вариантов: по сто на каждую категорию.
Копирование готового ключа от другого варианта дало 31 успешный
результат, около 3,4%. Собственные правильные ключи прошли все тесты.
Этот эксперимент проверяет механику, а точность грейдов предстоит
проверить экспертами и реальными кандидатами.

Если спросят о подборе: двенадцать заранее размеченных синтетических
запросов дали среднюю precision@k 1,00. Набор мал и совпадает с данными
разработки, поэтому это регрессионный результат, не рыночная метрика.

## 7. Стек и хранение

React и TypeScript на фронтенде, Go на сервере. PostgreSQL сохраняет
результаты, правила тестирования и приглашения. Redis хранит сессии
и ограничения запросов. Модульный монолит упрощает запуск хакатонного
стенда; API документируется OpenAPI.

## 8. Следующий этап

Дальше нужна независимая разметка качества подбора и калибровка банка
тестов. ФСП ID планируется через OIDC/Keycloak после появления контракта
данных. Для ATS предложены подписанные события приглашений.
Для внешнего стенда нужны домен, HTTPS и SMTP.

Не выдавать демонстрационные достижения за сведения реального реестра
или механические проверки за доказанную точность найма.
