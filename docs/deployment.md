# Стенд fsp.swek.tech и автоматический деплой

Адрес: **https://fsp.swek.tech**. Сервер: `161.104.34.75`, Ubuntu 24.04.
Это демонстрационный стенд с `APP_ENV=demo`, `DEMO_SEED=true` и теми же
демоаккаунтами, что при локальном запуске. HTTPS и защищённые cookies включены.

## Что происходит после коммита

Workflow `.github/workflows/ci.yml` запускается на push и pull request:

1. Go: `go test ./... -race -count=1` с настоящими PostgreSQL и Redis,
   `go vet ./...`, проверки ограничений протокола деплоя.
2. Frontend: `npm ci`, проверка TypeScript и production-сборка Vite.
3. Только после успеха обоих заданий коммит из `main` собирается в два
   Docker-образа. Ветки и pull request не получают ключа деплоя.
4. GitHub передаёт образы по SSH пользователю `fsp-deploy`. Сервер проверяет
   названия образов и метки SHA, сохраняет резервную копию БД, обновляет
   контейнеры ФСП и проверяет API, его зависимости и SHA фронтенда.
5. Workflow проверяет публичный HTTPS, `/api/health` и `/release.json`.

Параллельные деплои запрещены на уровне GitHub и блокировки на сервере.
Устаревший коммит пропускается, если перед сборкой в `main` уже есть новый:
так поздно завершившаяся проверка не возвращает старую версию.
При провале тестов работающая версия остаётся на месте. При провале запуска
или проверки сервер автоматически возвращает предыдущие образы.
Хранятся последние пять успешных версий (также текущая и предыдущая)
и 14 последних резервных копий; очистка касается только образов и копий ФСП.
Ручной повтор доступен через **Actions → Test and deploy FSP → Run workflow**,
ветка `main`.

## Изоляция на общем сервере

| Ресурс | Только ФСП |
| --- | --- |
| Docker Compose project / network | `fsp-career` / `fsp-career_default` |
| PostgreSQL, Redis, Mailpit volumes | `fsp-career_postgres-data`, `fsp-career_redis-data`, `fsp-career_mailpit-data` |
| Приложение | `127.0.0.1:18080`; снаружи доступно через HTTPS Nginx |
| Почта стенда | `127.0.0.1:18025`; публичного интерфейса нет |
| Конфигурация | `/opt/fsp-career/compose.yaml`, `/etc/fsp-career/service.env` |
| Деплой и журнал | `/usr/local/sbin/fsp-deploy`, `/opt/fsp-career/deployments.jsonl` |
| Резервные копии | `/opt/fsp-career/backups/*.sql.gz` |
| Текущая версия | `/opt/fsp-career/current-revision` |
| Nginx | отдельный vhost `/etc/nginx/sites-available/fsp.swek.tech` |
| Сертификат | отдельный Let's Encrypt `fsp.swek.tech`; webroot `/var/lib/fsp-career/acme` |

Порты БД и Redis не опубликованы. Все контейнеры имеют ограничения CPU,
памяти и размера логов; максимальная суммарная память — 768 MiB.
Сборка проходит на GitHub, на сервер приходят готовые образы.
Деплой не перезапускает Nginx или Docker и не выполняет общий `docker prune`,
`compose down` либо удаление volumes. Nginx только перечитывает конфигурацию
при первоначальной настройке домена и обновлении его сертификата после `nginx -t`.

Ключ GitHub не даёт shell, SFTP, переадресацию портов или членство в группе
`docker`. SSH `restrict` и forced command разрешают только фиксированный,
принадлежащий root обработчик. Пользователь не может менять Compose или
переменные окружения. Образы чужих сервисов обработчик отклоняет до `docker load`.
Root-ключи, пароль БД и SMTP не находятся в репозитории или workflow.

## Первоначальная настройка и обслуживание

Настройка уже выполнена. Для восстановления нового сервера администратор
копирует файлы `infra/deploy/` и `compose.deploy.yaml` в отдельную временную
папку, помещает Compose рядом с `bootstrap.sh` и выполняет:

```sh
sudo bash bootstrap.sh ./deploy-key.pub
```

До этого DNS `fsp.swek.tech` должен указывать на сервер, порты 80/443 должны
быть доступны, Docker Compose и Nginx/Certbot — установлены. Скрипт добавляет
только ресурсы ФСП. SSH host key нужно сверить через доверенное подключение.
GitHub Secrets: `FSP_DEPLOY_KEY` (отдельный приватный ключ OpenSSH),
`FSP_KNOWN_HOSTS` (проверенная запись host key сервера).

Привилегированные файлы `compose.deploy.yaml`, обработчик и Nginx обновляет
администратор отдельно: workflow намеренно не принимает произвольный Compose
от CI. Изменения приложения разворачиваются автоматически.

Проверка соседних систем после обслуживания:

```sh
sudo python3 /opt/fsp-career/verify-neighbors.py verify /opt/fsp-career/neighbors-before.json
```

Она сравнивает ID и время запуска исходных контейнеров, контрольные суммы
существовавших конфигураций Nginx и HTTP-статусы соседних сайтов. Если другой
администратор намеренно обновил соседний сервис, старый снимок требует
пересмотра; это не проверка всех функций сторонних приложений.

Просмотр ФСП:

```sh
sudo env FSP_REVISION="$(cat /opt/fsp-career/current-revision)" \
  docker compose -p fsp-career --env-file /etc/fsp-career/service.env \
  -f /opt/fsp-career/compose.yaml ps
```

Ручной откат на SHA ранее успешно развёрнутого образа:

```sh
printf 'rollback %s\n' FULL_PREVIOUS_COMMIT_SHA | sudo /usr/local/sbin/fsp-deploy
```

Откат возвращает код, сохраняя данные. Автоматическое восстановление дампа
не выполняется: оно потеряло бы записи, созданные после копирования. Текущие
миграции совместимы с возвратом к предыдущему приложению; перед будущими
удаляющими миграциями нужен отдельный план совместимости.

## Почта

Сейчас письма регистрации и восстановления попадают в приватный Mailpit,
как на локальном стенде. Для их просмотра администратор открывает туннель:

```sh
ssh -L 18025:127.0.0.1:18025 root@161.104.34.75
```

И затем `http://127.0.0.1:18025`. На реальные адреса письма не отправляются.
Для пилота нужно прописать реальные `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`,
`SMTP_USER`, `SMTP_PASSWORD` в `/etc/fsp-career/service.env`, отключить демо
и использовать `APP_ENV=production`. В production SMTP обязан поддерживать
STARTTLS. Демонстрационные аккаунты и данные не переносят в настоящую базу.

Не используйте команды остановки, очистки образов или удаления данных без
точного project name `fsp-career`. Удалять можно лишь проверенные старые
образы `fsp-career-api:*`, `fsp-career-web:*` и собственные копии ФСП,
сохраняя текущую и предыдущую рабочую версию.
